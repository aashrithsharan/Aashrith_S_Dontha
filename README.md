### 🧭 How I work

**Find where users stall, fix the cause not the symptom, prove it with an experiment.**

<details>
<summary><b>Three opinions I've earned the hard way</b></summary>

<br>

**Design the exception path as carefully as the happy path.** I once specced a happy path thoroughly and shipped a flow that showed some users a blank screen on decline. That's a product failure, not an engineering one. Decline, timeout and reversal paths are in my first PRD draft now, not my last.

**Own your failure behaviour.** I tried a no-code workflow tool for my integrations and walked away from it — retries, failure modes and data contracts were opaque exactly when things broke. I'd rather build the integration and own all three.

**Standards that touch an engineer's sprint get co-designed, or they get worked around.** I introduced documentation-as-definition-of-done without doing that. Three PRs blocked in sprint one. The policy was right; the rollout was wrong.

</details>
